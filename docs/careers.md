# Careers and applications

Uses the existing website Firestore project. No new Firebase project, OAuth client, storage bucket, or hosting service is needed. Production still needs the existing Roblox account-linking OAuth configuration and public Roblox approval from the account work.

## Team workflow

1. Open **Careers → Manage openings**, or **Admin → Careers & applications**. Existing Developer access includes the site's mapped Discord Owner/Admin roles. QA Leads have a separate read-only **QA applications** page for Quality Assurance submissions. QA Testers cannot access private applications.
2. Choose **New opening**. Start from a Tester, Moderator, or Developer template, or build from scratch. Templates are editable drafts, not published recruitment terms; review the commitment, description, and questions yourself.
3. Add short/long answers, multiple choice, checkboxes, ranking, or linear scales. Set required questions, help text, options, scale labels, a deadline, and the confirmation message. Questions can be moved, duplicated, and removed. Select text in any opening detail, question, help text, choice option, or scale label to use bold, italic, underline, strikethrough, text/highlight colours, text size, links, or clear formatting. Descriptions and confirmation messages also support list items. Undo/redo and the existing character limits are available in each editor. Attach one PNG/JPG image per question using the existing R2 storage (up to 5 MB); add an image description before publishing. Removing an image detaches it from the next version; previous published versions retain it.
4. **Save draft** saves an explicit draft. **Preview** lets you try the question controls without submitting. **Publish opening/version** confirms the current draft and makes it public.
5. **Close opening** stops new applications. It keeps existing submissions available. Publishing again reopens it; choose a future deadline or clear the old one first.
6. Open **Review applications**, either for one opening or all openings. Filter by status and use Next/Previous for more records. Read original answers, select a status, write optional applicant feedback and/or private notes, and **Save review**. The top of the queue shows distinct applicants and total applications, with category and opening breakdowns across all matching pages. The selected status/opening filters apply to these counts; QA Leads only receive QA counts. A person applying to more than one opening counts once in the total applicants. Each written answer shows a word count, with the written-answer total beneath the submission. Selected options, rankings, scales, and question text do not contribute to the word count. Reviewer feedback and private notes use the same formatting tools; notes and their styles remain restricted to reviewers.

Statuses: Submitted, Under review, Shortlisted, Accepted, Rejected, Withdrawn. Opening an application does not silently change its status; reviewers explicitly save their decision. Decisions do not send messages or grant platform roles.

Applicants sign in through the existing Discord flow and connect Roblox through Account → Connections. Both are checked again on submission, including the Roblox ownership claim. Applications are available under Account → Applications and as a recent preview on the profile overview. The details view shows submitted answers, feedback, and the latest 50 public status/feedback changes. Applicants can withdraw an undecided application, with confirmation. There is one submission per Discord account per opening, including after withdrawal; create a **new opening** for a new recruitment round. Existing Google Forms submissions are not imported.

## Data and cost design

- `careerForms/{randomId}`: opening metadata and editable draft. Public queries only return metadata for published, unexpired openings. Public listings have a bounded 60-second server cache, invalidated by edits. Submission checks always read the authoritative opening.
- `careerQuestionImages/{randomId}`: upload metadata for question images in the existing R2 bucket. Draft images are Developer-only; publication makes ready images available to authenticated readers. Uploads use signed URLs and check object size/type before attachment. Image references are validated against the opening inside the draft/publish transaction; bytes are never embedded in Firestore. Unreferenced uploads are retained, so include them in periodic storage/retention reviews.
- `careerFormVersions/{openingId_revision}`: immutable questions and description, one document per published version. Applications reference this instead of copying every question into every response. Draft saves do not generate published versions.
- `careerApplications/{hash(openingId:discordId)}`: identity snapshot, validated answers, status, feedback, private notes, and bounded history. Deterministic IDs and Firestore transactions prevent duplicate writes on concurrent/retried submission. Edits use revision checks to prevent overwriting another reviewer or a withdrawal.
- One application document write on first submission, one on review/withdrawal. No database writes for typing, previewing, or opening a submission; no polling and no notification fan-out. Transactions may perform additional reads on conflicts.
- Lists return at most 20 summaries plus a lookahead document (21 reads maximum per query), cursor-paginated with a document ID tie-breaker. Answers, private notes, and history are excluded from list projections. An application detail normally reads its application plus one shared form version. Applicant submission also reads the profile, Roblox ownership claim, existing application, opening, and published version.
- Admin counts read only applicantId/category/formId/title/createdAt projections in batches of at most 500, using existing application list indexes. Totals are cached for up to 60 seconds per role/filter and invalidated locally on submit/review/withdrawal. A cache miss reads every matching application summary to deduplicate people and group categories/openings; this is additional read cost, independent of the 21-document list query budget. There is no polling or count backfill.
- Formatting is optional, validated styled-text runs alongside the original strings. No arbitrary HTML/CSS is accepted for rendering; links permit only HTTP, HTTPS and mailto. Old unformatted forms/reviews keep working, and published versions preserve their formatting and images. The existing plain-text answer identities and limits are unchanged.
- Form maximum: 40 questions, 15 options each. Answers maximum: 64 KB UTF-8 total; 500 characters per short answer and 5,000 per long answer. Feedback is limited to 2,000 characters, notes to 6,000, history to the latest 50 public changes. These are bounds per record, not a promise of fixed total storage cost.
- Large question, answer, note, and history fields have index exemptions. Only list/filter fields are indexed. This follows [Firestore guidance on index exemptions and cursors](https://firebase.google.com/docs/firestore/best-practices).
- New records go into Firestore, not local `.runtime`. Local runtime caches/sessions continue to follow the existing host's persistence setup. No large application archive is placed on the host's 4 GB disk.

## Database preparation before deployment

`firestore.indexes.json` includes the new Careers indexes and field exemptions alongside the existing account indexes. The existing setup script has been generalized; both the old `account:indexes` command and the clearer new name below run it.

```sh
npm run db:indexes
# With credentials authorized to administer Firestore indexes:
npm run db:indexes -- --apply
# To create only the four QA application indexes:
npm run db:indexes -- --apply --only-qa-careers
# Repeat the read-only check until all indexes are READY:
npm run db:indexes
```

The script is additive and leaves unrelated indexes alone. It applies the explicit field exemptions/overrides in the file. The current application service account previously lacked permission to create indexes; an authorized project administrator may need to run this or use the Firebase console. Do not add broad index-administration privileges to the runtime application just for this step.

Required composites: `careerForms` state ASC + openUntil ASC; `careerApplications` createdAt DESC following each of these equality-filter sets: applicantId; status; formId; formId+status; applicantId+status; applicantId+formId; applicantId+formId+status; category; category+status; category+formId; category+formId+status. Firestore adds its document-name tie-breaker. `careerForms` and `careerApplications` each retain a descending single-field createdAt index; the wildcard automatic index exemption disables unnecessary fields. `careerFormVersions` needs no field indexes.

The repository’s `firestore.rules` denies all direct client reads and writes, including the new collections. Keep that rule deployed. This application uses authenticated server REST access. Check existing Firestore security rules do not grant broad public access to arbitrary collections. Server routes enforce applicant ownership, QA Lead read-only access to Quality Assurance applications, and Developer-only application changes; Firestore Admin credentials bypass client security rules, so both boundaries matter.

After deployment, verify `/careers`, one real Discord/Roblox link, a draft/preview/publish cycle, a submission, a reviewer update, and the applicant's tracker. Ensure `/api/careers/*` goes to Node with API caching disabled and SPA paths reach `index.html`, following the current hosting setup. Existing API/header configuration is sufficient; no new CSP destinations were introduced.

### Listing fails with HTTP 503

Publishing a form does not prove that list queries are ready: document writes can work while a required composite index is missing. Run `npm run db:indexes` and wait for the relevant indexes to be `READY`. Index changes take effect without restarting the website.

The hosting error-page middleware can replace a JSON API error with the HTML maintenance page. Keep that middleware off the `/api/*` router so API status codes and JSON error bodies reach the client unchanged. Keep the maintenance page for normal page navigation. The backend logs `Careers query unavailable` with Firestore's diagnostic when a query lacks an index.

## Luna review setup

The review workspace selects one recruitment form at a time, including past rounds. Titles, dates, state and application counts distinguish forms. It remembers the selected form locally and in the URL. The explicit All forms overview supports browsing; search and ranked sorting require a selected form. QA Leads retain read-only access to QA applications and scores. Only Developers (including the existing mapped Owner/Admin roles) can change criteria, draft guides, start or cancel paid reviews.

In the form editor, **AI review guide** contains a plain-English brief, up to eight optional sample answers with marks and explanations, and up to eight named criteria with descriptions and optional low/middle/high anchors. **Draft guide with Luna** proposes an editable guide; it does not save or start a review. Each criterion is marked 0–5. Importance multiplies its contribution: Normal = 1, High = 2, Highest = 3; the editor shows the resulting percentage. Save draft persists these private settings without republishing the public form. Criteria and samples are kept outside published form versions and public/list projections.

Configure `OPENAI_API_KEY` in the ignored server `.env` or the deployment's secret environment. Optional `OPENAI_ORG_ID` and `OPENAI_PROJECT_ID` explicitly choose the API organisation/project; use the organisation linked to the operator's eligible subscription credit benefit. Never use a `VITE_` variable or put a real key in tracked files. Restart the backend after changing its environment. The integration uses `gpt-6-luna` through the Responses API, structured JSON outputs, low reasoning effort, a 6,000-output-token cap, a 45-second request timeout, and `store: false`. It does not automatically provision credits, recharge an account, or alter billing settings. Eligible subscription benefits are claimed through OpenAI's account flow, separately from the website's server key.

**Run AI review** snapshots the IDs of all current non-withdrawn applications for the selected form, across all pages and statuses (up to 5,000 application records per opening). UI search/status filters do not change the comparison pool. Each assessment receives the saved guide, role details, original published questions/options, the submitted answers and relevant question images. Identity columns, account IDs, existing statuses, feedback and private notes are excluded. Free-text answers and administrator-supplied examples can still contain personal details; use fictional or de-identified examples. Answers are split into ordered passages of at most 300 characters, preserving original text. Luna selects supporting passage IDs from an application-specific schema; the server resolves those IDs to the actual submitted text and question before storage. It does not rely on the model retyping an exact quote. Unknown references still fail validation; missing evidence may be an empty array. This verifies the source of a quote, not whether the AI's explanation or score is sound. The provider does not make acceptance decisions.

`careerAiRuns/{runId}` stores a frozen guide, cohort IDs, progress, requester, usage and lease. `careerAiRuns/{runId}/careerAiScores/{applicationId}` stores its assessment and computed scores. Form metadata stores the latest ten run IDs, an active-run pointer and the last completed-run pointer. History uses direct document reads, avoiding a new composite-index dependency. The worker's bounded state query uses the existing automatic state index; scores paginate by document ID. Recommended index exemptions for these private collections are in `firestore.indexes.json`. An index administrator can apply just those with `npm run db:indexes -- --only-careers-ai --apply` and verify using `--only-careers-ai --require-ready`. The runtime account may lack index-administration permission; these exemptions are an optional storage optimisation while the default state index remains enabled.

The server worker owns a transaction lease and advances the durable queue. Merely viewing a page never starts an AI request. Successful results replace the visible ranking only after the entire run completes. Failure/cancellation leaves the previous ranking intact. A process interruption during a potentially billed request fails that run instead of silently sending it twice; interrupted work between requests can resume. Cancelling cannot undo a request already sent. A subsequent button press re-evaluates the complete current cohort. New arrivals remain unranked until a completed run includes them. Changes to saved criteria mark prior scores as using previous criteria.

The criteria score is twice the weighted mean of 0–5 marks. Relative scores use normal-quantile rank positions centred on five with spread two, clamped to 0–10. Tied criteria scores share the average of their occupied positions, preserving the cohort mean of five before display rounding. Small/tied pools need not resemble a smooth normal distribution. Colour uses the list palette from red through orange/yellow to green; grey `-/10` means unranked. Status filters/search never recompute that curve. Results and evidence are available only through authorized admin application reads; applicants do not receive the AI assessment.

Admin list/detail reads add form-pointer and score-document reads. Search/oldest/score sorting scans bounded summary batches and minimal score projections to sort the entire selected pool before pagination; it never fetches answers for list sorting. Run status reads at most ten job documents and polls only while a run is queued/running. The worker probes its queue periodically while a key is configured. Every explicit review and guide-drafting request can incur API usage. There is no implicit per-submission review.

Validation: `npm test`, `npm run build`, `PLAYWRIGHT_CHANNEL=chrome node tests/browser/careers-ai.mjs` and the existing careers-authoring browser check. Tests use synthetic accounts, an in-memory database and injected provider responses. A separate small live Luna smoke check uses fictional content only. These checks do not establish production deployment, real applicant ranking quality or agreement with human reviewers.

## Privacy, retention, and support

Privacy and terms pages now describe applications, identity snapshots, reviewer access, and withdrawal. No automatic archive deletion is enabled: the operator must decide retention periods rather than silently lose recruitment records. Review storage periodically and fulfill verified access/deletion requests through `contact@towereclipse.com`.

For a verified privacy request, query `careerApplications` by applicantId and paginate all results. Applicant exports must exclude internalNotes and reviewer metadata unless the operator determines disclosure is appropriate under the applicable request; private notes may still need consideration when fulfilling legal rights. Application deletion removes its record including embedded history and notes. Also remove its derived careerAiScores documents and supporting excerpts from retained review runs when fulfilling an applicable deletion request; run membership IDs may need removal too. Administrator sample answers copied from an application must be considered separately. Deleting that record also removes the one-submission guard, so handle a retained minimal anti-abuse record only if justified and disclosed. Unlinking Roblox alone does not erase historical application identity snapshots. A shared form version contains form questions rather than applicant answers and must not be removed while applications reference it.
