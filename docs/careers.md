# Careers and applications

Uses the existing website Firestore project. No new Firebase project, OAuth client, storage bucket, or hosting service is needed. Production still needs the existing Roblox account-linking OAuth configuration and public Roblox approval from the account work.

## Team workflow

1. Open **Careers → Manage openings**, or **Admin → Careers & applications**. Existing Developer access includes the site's mapped Discord Owner/Admin roles. QA Leads have a separate **QA applications** page for Quality Assurance submissions; they can read applications and manage their own read markers, while decisions, feedback, notes and openings remain Developer-only. QA Testers cannot access private applications.
2. Choose **New opening**. Start from a Tester, Moderator, or Developer template, or build from scratch. Templates are editable drafts, not published recruitment terms; review the commitment, description, and questions yourself.
3. Add short/long answers, multiple choice, checkboxes, ranking, or linear scales. Set required questions, help text, options, scale labels, a deadline, and the confirmation message. Questions can be moved, duplicated, and removed. Select text in any opening detail, question, help text, choice option, or scale label to use bold, italic, underline, strikethrough, text/highlight colours, text size, links, or clear formatting. Descriptions and confirmation messages also support list items. Undo/redo and the existing character limits are available in each editor. Attach one PNG/JPG image per question using the existing R2 storage (up to 5 MB); add an image description before publishing. Removing an image detaches it from the next version; previous published versions retain it.
4. **Save draft** saves an explicit draft. **Preview** lets you try the question controls without submitting. **Publish opening/version** confirms the current draft and makes it public.
5. **Close opening** stops new applications. It keeps existing submissions available. Publishing again reopens it; choose a future deadline or clear the old one first.
6. Open **Review applications**, either for one opening or all openings. Filter by status and use Next/Previous for more records. Read original answers, select a status, write optional applicant feedback and/or private notes, and **Save review**. The top of the queue shows distinct applicants and total applications, with category and opening breakdowns across all matching pages. The selected status/opening filters apply to these counts; QA Leads only receive QA counts. A person applying to more than one opening counts once in the total applicants. Each written answer shows a word count, with the written-answer total beneath the submission. Selected options, rankings, scales, and question text do not contribute to the word count. Reviewer feedback and private notes use the same formatting tools; notes and their styles remain restricted to reviewers.

Statuses: Submitted, Under review, Shortlisted, Accepted, Rejected, Withdrawn. Opening an application does not silently change its status; reviewers explicitly save their decision. Decisions do not send messages or grant platform roles. Administrators can restore a Withdrawn application by selecting any other status and saving the review, including after the opening closes. The withdrawal remains in the timeline; QA Leads cannot restore applications or change review decisions, feedback or notes.

Developers and QA Leads can explicitly choose **Mark Application as Read** on applications they can access. The detail and review queue distinguish **READ BY YOU**, **READ BY OTHERS**, and **UNREAD BY TEAM**; the detail also lists reader names and read times. Opening an application does not mark it read. Each reviewer can mark it unread for themselves without clearing anyone else's marker. Read markers are private to authorized reviewers and do not affect status, applicant feedback, the public timeline or unsaved review edits. They reset on applicant resubmission so updated answers need a fresh read. A stale tab cannot mark a newer submission read; reload and read the updated answers first. Refresh the queue to fetch changes made by other sessions.

Applicants sign in through the existing Discord flow and connect Roblox through Account → Connections. Both are checked again on submission, including the Roblox ownership claim. Applications are available under Account → Applications and as a recent preview on the profile overview. The details view shows submitted answers, feedback, and the latest 50 public status/feedback changes. Applicants can withdraw an undecided application, with confirmation. Applicants can choose **Edit application** on their application detail page, update their prefilled answers, confirm the privacy notice, and **Resubmit application** while the current published opening is open and before its current deadline. With no deadline, editing stays available until the opening closes. The editor retains the original published questions even when a later version is published. Edits remain on the page until explicitly resubmitted; cancelling keeps the saved submission unchanged. Resubmission replaces the answers on the same application, returns its status to Submitted, clears the current decision feedback and reviewer, and preserves private notes, the original account snapshot/submission date, and the latest 50 public timeline events. Previous feedback remains in that timeline. Withdrawn applications require administrator restoration before editing. There is one application record per Discord account per opening; create a **new opening** for a new recruitment round. Existing Google Forms submissions are not imported.

Applicants can also choose **Save draft** before submitting, or while editing an existing application. Required answers and privacy consent are checked on submission; an explicit draft save can contain unfinished writing. Saved drafts are private to their owner, resume from the same opening/application on another visit or device, and never appear in submitted lists, counts, reviewer views or AI requests. Saving edited answers does not alter the current submission or its status. There is no autosave or polling. Unchanged saves do not write. Saving in another tab causes a revision conflict instead of silently replacing newer work. If published questions change, the latest form carries over only answers to exactly unchanged questions and shows the previous draft for recovery. Saving the new version explicitly replaces the old draft. Acknowledged drafts are removed in the successful submit/resubmit transaction; drafts never extend the opening deadline. Owners can reopen an expired/closed opening to read their retained draft, with saving/submission disabled.

## Data and cost design

- `careerForms/{randomId}`: opening metadata and editable draft. Public queries only return metadata for published, unexpired openings. Public listings have a bounded 60-second server cache, invalidated by edits. Submission checks always read the authoritative opening.
- `careerQuestionImages/{randomId}`: upload metadata for question images in the existing R2 bucket. Draft images are Developer-only; publication makes ready images available to authenticated readers. Uploads use signed URLs and check object size/type before attachment. Image references are validated against the opening inside the draft/publish transaction; bytes are never embedded in Firestore. Unreferenced uploads are retained, so include them in periodic storage/retention reviews.
- `careerFormVersions/{openingId_revision}`: immutable questions and description, one document per published version. Applications reference this instead of copying every question into every response. Draft saves do not generate published versions.
- `careerApplicationDrafts/{hash(openingId:discordId)}`: private partial answers, saved form version, optimistic draft revision, and (for edited submissions) the acknowledged application revision. Only deterministic document reads are used; no collection scan or composite index is needed. Loading an applicant form/detail adds one draft lookup, with one additional original-version read only if questions changed. A changed draft save reads 4 documents for an existing application or 6 for a new application (including linked-account checks), then writes one draft. No write occurs merely from typing.
- `careerApplications/{hash(openingId:discordId)}`: identity snapshot, validated answers, status, feedback, private notes, bounded history, and private per-reviewer read receipts. Deterministic IDs and Firestore transactions prevent duplicate writes on concurrent/retried submission. Edits use revision checks to prevent overwriting another reviewer or a withdrawal. Read marking uses a separate submission-revision check and a transaction that updates only the current reviewer's receipt; it does not increment the application's review revision or update its modification time. Repeating the same marker action does not write again. Existing applications without receipts start unread; no migration or additional Firestore indexes are needed.
- One application document write on first submission, one on review/withdrawal. Resubmission updates the existing application and an edit counter on its opening in one transaction; revision checks prevent overwriting a concurrent review, withdrawal, or another resubmission, and the opening/deadline are checked again before saving. No database writes for typing, previewing, or opening a submission; no polling and no notification fan-out. Transactions may perform additional reads on conflicts.
- Lists return at most 20 summaries plus a lookahead document (21 reads maximum per query), cursor-paginated with a document ID tie-breaker. Answers, private notes, and history are excluded from list projections. An application detail reads its application, shared original form version, and current opening to determine editing eligibility. Applicant submission also reads the profile, Roblox ownership claim, existing application, opening, and published version.
- Admin counts use a bounded compact role/opening corpus, retaining exact distinct-person/category/opening counts across status filters. Cold fills read summary batches of at most 500; subsequent filters reuse them, and committed local mutations update the read model incrementally. Notes/feedback-only changes do not rebuild counts. External-process freshness is bounded to 15 minutes, with a visible timestamp and explicit Refresh. Drafts are excluded. Legacy selectors may need one scoped QA reconciliation; unknown historical opening counts display a dash rather than an incorrect zero.
- Formatting is optional, validated styled-text runs alongside the original strings. No arbitrary HTML/CSS is accepted for rendering; links permit only HTTP, HTTPS and mailto. Old unformatted forms/reviews keep working, and published versions preserve their formatting and images. The existing plain-text answer identities and limits are unchanged.
- Form maximum: 40 questions, 15 options each. Answers maximum: 64 KB UTF-8 total; 500 characters per short answer and 5,000 per long answer. Feedback is limited to 2,000 characters, notes to 6,000, history to the latest 50 public changes. These are bounds per record, not a promise of fixed total storage cost.
- Large question, answer, note, and history fields have index exemptions. Only list/filter fields are indexed. This follows [Firestore guidance on index exemptions and cursors](https://firebase.google.com/docs/firestore/best-practices).
- New records go into Firestore, not local `.runtime`. Local runtime caches/sessions continue to follow the existing host's persistence setup. No large application archive is placed on the host's 4 GB disk.

## Database preparation before deployment

`firestore.indexes.json` includes the new Careers indexes and field exemptions alongside the existing account indexes. The existing setup script has been generalized; both the old `account:indexes` command and the clearer new name below run it.

```sh
npm run db:indexes
# With credentials authorized to administer Firestore indexes:
npm run db:indexes -- --apply
# To create only the four QA application indexes:
npm run db:indexes -- --apply --only-qa-careers
# Repeat the read-only check until all indexes are READY:
npm run db:indexes
```

The script is additive and leaves unrelated indexes alone. It applies the explicit field exemptions/overrides in the file. The current application service account previously lacked permission to create indexes; an authorized project administrator may need to run this or use the Firebase console. Do not add broad index-administration privileges to the runtime application just for this step.

Required composites: `careerForms` state ASC + openUntil ASC; `careerApplications` createdAt DESC following each of these equality-filter sets: applicantId; status; formId; formId+status; applicantId+status; applicantId+formId; applicantId+formId+status; category; category+status; category+formId; category+formId+status. Firestore adds its document-name tie-breaker. `careerForms` and `careerApplications` each retain a descending single-field createdAt index; the wildcard automatic index exemption disables unnecessary fields. `careerFormVersions` needs no field indexes.

The repository’s `firestore.rules` denies all direct client reads and writes, including the new collections. Keep that rule deployed. This application uses authenticated server REST access. Check existing Firestore security rules do not grant broad public access to arbitrary collections. Server routes enforce applicant ownership, QA Lead reads and personal read markers for Quality Assurance applications, and Developer-only review/status changes; applicant answer changes use a separate ownership-checked resubmission route; Firestore Admin credentials bypass client security rules, so both boundaries matter. The read-marker endpoint has the same authentication, CSRF and same-origin protection as other application writes, and callers cannot select another reviewer's receipt.

After deployment, verify `/careers`, one real Discord/Roblox link, a draft/preview/publish cycle, a submission, a reviewer update, and the applicant's tracker. Ensure `/api/careers/*` goes to Node with API caching disabled and SPA paths reach `index.html`, following the current hosting setup. Existing API/header configuration is sufficient; no new CSP destinations were introduced.

### Listing fails with HTTP 503

Publishing a form does not prove that list queries are ready: document writes can work while a required composite index is missing. Run `npm run db:indexes` and wait for the relevant indexes to be `READY`. Index changes take effect without restarting the website.

The hosting error-page middleware can replace a JSON API error with the HTML maintenance page. Keep that middleware off the `/api/*` router so API status codes and JSON error bodies reach the client unchanged. Keep the maintenance page for normal page navigation. The backend logs `Careers query unavailable` with Firestore's diagnostic when a query lacks an index.

## AI review setup

The review workspace selects one recruitment form at a time, including past rounds. Titles, dates, state and application counts distinguish forms. It remembers the selected form locally and in the URL. The explicit All forms overview supports browsing; search and ranked sorting require a selected form. QA Leads retain read-only access to QA applications and scores. Only Developers (including the existing mapped Owner/Admin roles) can change criteria, draft guides, start or cancel paid reviews.

In the form editor, **AI review guide** contains a plain-English brief, up to 20 optional sample answers with marks and explanations, and up to eight named criteria with descriptions and optional low/middle/high anchors. **Draft guide with Luna** proposes an editable guide; it does not save or start a review. Each criterion is marked 0–5. Importance multiplies its contribution: Normal = 1, High = 2, Highest = 3; the editor shows the resulting percentage. Save draft persists these private settings without republishing the public form. Criteria and samples are kept outside published form versions and public/list projections.

Configure `OPENAI_API_KEY` in the ignored server `.env` or the deployment's secret environment. Optional `OPENAI_ORG_ID` and `OPENAI_PROJECT_ID` explicitly choose the API organisation/project; use the organisation linked to the operator's eligible subscription credit benefit. Never use a `VITE_` variable or put a real key in tracked files. Restart the backend after changing its environment. Reviews use the Responses API, structured JSON outputs and `store: false`, with the existing server key. They do not automatically provision credits, recharge an account, or alter billing settings. Eligible subscription benefits are claimed through OpenAI's account flow, separately from the website's server key.

Before **Run AI review**, choose **GPT-6 Luna** (`gpt-6-luna`) or **GPT-6.1 Sol** (`gpt-6.1-sol`) and Low, Medium, High, Extra high or Maximum reasoning effort. New reviews default to Luna with Medium effort. These choices are frozen for that run; changing the controls affects a future run and never starts a request by itself. Queued historical runs without a saved effort keep their original Low behaviour. **Draft guide with Luna** continues to use Luna with Low effort. Higher effort allows more reasoning tokens and time; it does not guarantee more consistent or accurate scores. The panel shows selected Standard USD token rates and the model/effort used by current and historical reviews. Token totals include cached-input and reasoning breakdowns when returned by the provider; those are subsets of total input/output tokens, not extra tokens to add. Displayed rates are informational estimates rather than an account balance or final bill.

Request allowances depend on effort: Low permits 6,000 output tokens, Medium 16,000, High 32,000, Extra high 48,000 and Maximum 64,000. This allowance includes reasoning and final output. Low/Medium requests have a three-minute deadline; High/Extra high/Maximum have a five-minute deadline. The worker holds a ten-minute transaction lease, longer than the request deadline, so another worker cannot reclaim an active long request. These are website limits, not the models' maximum context/output capacities or the API organisation's rate limits. Requests remain sequential and incomplete output never replaces the last completed ranking.

**Run AI review** snapshots the IDs of all current non-withdrawn applications for the selected form, across all pages and statuses (up to 5,000 application records per opening). UI search/status filters do not change the comparison pool. Each assessment receives the saved guide, role details, original published questions/options, the submitted answers and relevant question images. Identity columns, account IDs, existing statuses, feedback and private notes are excluded. Free-text answers and administrator-supplied examples can still contain personal details; use fictional or de-identified examples. Answers are split into ordered passages of at most 300 characters, preserving original text. The selected model receives every passage and selects supporting passage IDs from an application-specific schema; the server resolves those IDs to the actual submitted text and question before storage. It does not rely on the model retyping an exact quote. Unknown references still fail validation; missing evidence may be an empty array. This verifies the source of a quote, not whether the AI's explanation or score is sound. The provider does not make acceptance decisions.

`careerAiRuns/{runId}` stores a frozen guide, cohort IDs, model, reasoning effort, prompt version, progress, requester, usage and lease. `careerAiRuns/{runId}/careerAiScores/{applicationId}` stores its assessment and computed scores. Form metadata stores the latest ten run IDs, an active-run pointer and the last completed-run pointer with its model/effort. History uses direct document reads, avoiding a new composite-index dependency. The worker's bounded state query uses the existing automatic state index; scores paginate by document ID. Recommended index exemptions for these private collections are in `firestore.indexes.json`. An index administrator can apply just those with `npm run db:indexes -- --only-careers-ai --apply` and verify using `--only-careers-ai --require-ready`. The runtime account may lack index-administration permission; these exemptions are an optional storage optimisation while the default state index remains enabled.

The server worker owns a transaction lease and advances the durable queue. Merely viewing a page never starts an AI request. Successful results replace the visible ranking only after the entire run completes. Failure/cancellation leaves the previous ranking intact. A process interruption during a potentially billed request fails that run instead of silently sending it twice; interrupted work between requests can resume. Cancelling cannot undo a request already sent. A subsequent button press re-evaluates the complete current cohort. New arrivals remain unranked until a completed run includes them. Changes to saved criteria mark prior scores as using previous criteria. Resubmitted answers get a separate submission revision; scores for earlier revisions are hidden and excluded from ranked sorting until an administrator explicitly reruns the review. A resubmission during a queued/running review invalidates that run before it can apply a new ranking. Resubmission never starts a paid AI request.

The assessment prompt and grading calculation stay the same across model/effort choices. Each application is evaluated independently against the same saved guide; the model does not receive the other applications, previous assessments or shared conversation memory. There is no additional cohort-comparison or score-adjustment stage. The criteria score is twice the weighted mean of 0–5 marks. Relative scores use normal-quantile rank positions centred on five with spread two, clamped to 0–10. Tied criteria scores share the average of their occupied positions, preserving the cohort mean of five before display rounding. Small/tied pools need not resemble a smooth normal distribution. Colour uses the list palette from red through orange/yellow to green; grey `-/10` means unranked. Status filters/search never recompute that curve. Results and evidence are available only through authorized admin application reads; applicants do not receive the AI assessment.

Oldest-first sorting uses ascending 21-document database cursor pages. Search and ranked sorting reuse bounded role/opening summary and completed-score indexes; a cold fill still reads the complete supported pool once, while subsequent pages fetch at most 20 current application rows. Normal row badges read only visible compact score documents on a cold cache; detailed grades load on application detail. Published form versions and image metadata are cached without skipping mutable deadline/revision checks. Active-run polling reads only the active job, pauses while hidden, and loads history explicitly. Idle worker discovery backs off from 15 seconds to five minutes, while a new local job wakes it immediately; claimed jobs remain leased and durable. Every explicit review and guide-drafting request can incur API usage. There is no implicit per-submission review.

Validation: `npm test`, `npm run build`, `PLAYWRIGHT_CHANNEL=chrome node tests/browser/careers-ai.mjs` and the existing careers-authoring browser check. `PLAYWRIGHT_CHANNEL=chrome node tests/browser/careers-resubmission.mjs` verifies original-version prefill for all six answer types, cancellation, explicit resubmission, status/history/private-note handling, administrator restoration, QA read-only access, late-submit refusal preserving typed edits, and mobile width using synthetic fixtures. Model/effort tests cover request validation, frozen options, historical defaults, token usage, longer leases and safe interrupted-run recovery. Tests use synthetic accounts, an in-memory database and injected provider responses; the model/effort upgrade makes no live OpenAI requests. These checks do not establish model access for the deployed key, production deployment, real applicant ranking quality or agreement with human reviewers.

## Privacy, retention, and support

Privacy and terms pages now describe applications, identity snapshots, reviewer access, and withdrawal. No automatic archive deletion is enabled: the operator must decide retention periods rather than silently lose recruitment records. Review storage periodically and fulfill verified access/deletion requests through `contact@towereclipse.com`.

For a verified privacy request, include private `careerApplicationDrafts` records as well as submitted applications. Draft records use deterministic opening/account IDs; no account-list index is needed for normal editing. If administrators need a bulk owner lookup for support, use a deliberate bounded maintenance process or add the required owner index rather than scanning drafts on routine requests. For submitted applications, query `careerApplications` by applicantId and paginate all results. Applicant exports must exclude internalNotes and reviewer metadata unless the operator determines disclosure is appropriate under the applicable request; private notes may still need consideration when fulfilling legal rights. Application deletion removes its record including embedded history and notes. Also remove its derived careerAiScores documents and supporting excerpts from retained review runs when fulfilling an applicable deletion request; run membership IDs may need removal too. Administrator sample answers copied from an application must be considered separately. Deleting that record also removes the one-submission guard, so handle a retained minimal anti-abuse record only if justified and disclosed. Unlinking Roblox alone does not erase historical application identity snapshots. A shared form version contains form questions rather than applicant answers and must not be removed while applications reference it.
